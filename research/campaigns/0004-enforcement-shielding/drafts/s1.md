# Task: acquire IBAMA fines and embargoes, from IBAMA's portal or Base dos Dados on BigQuery (build, idea 0005)

## Goal

Two acquire scripts, `pipeline/acquire/ibama_autos.py` and
`pipeline/acquire/ibama_embargos.py`, each storing one Parquet of IBAMA
records for the Legal Amazon states. Neither may store, or on the BigQuery
path even download, a personal identifier. Each tries IBAMA's open-data
portal first. If anything on that path fails, the same run falls back to
Base dos Dados on BigQuery. Both sources give the same Parquet schema,
defined once per dataset in its data contract.

Campaign `research/campaigns/0004-enforcement-shielding/campaign.md`, step
s1. Steps s2 and s3 run these scripts once each through `data-pipeline`
(`stage=acquire`); step s4 builds `cell_enforcement` from their output.

## Idea

Idea 0005 (`research/ideas/0005-enforcement-shielding.md`), linked to idea
0001. The data rules are in `AGENTS.md` ("Data", "Personal identifiers")
and decision 0003 (outcome data: raw holds both halves, no exploration
account reads raw). This is a **build** task: it may change exactly the
files below.

### Rules that bind this code

- **No URL or raw folder in code.** `tests/test_acquire.py::test_no_url_or_dataset_folder_in_code`
  fails if `https://` or any catalog `gcs:` folder appears in a file under
  `pipeline/` or `src/terrain/`. Every URL lives in `data/catalog.yaml`:
  - the portal pages and files;
  - the Base dos Dados page;
  - the BigQuery endpoint `https://bigquery.googleapis.com/bigquery/v2/`;
  - the OAuth scope `https://www.googleapis.com/auth/bigquery`.

  The table ids live there too.
- **Personal identifiers.**
  - Names, CPF/CNPJ, property names, free text and geometries never reach
    a stored file, a manifest, a log line or an exception message.
  - On the BigQuery path they are never selected. The query builder raises
    if a column name starts with `cpf_cnpj` or `nome`, or equals
    `geometria`, even if the catalog lists it.
  - Tests use only synthetic values built in the test.
- **Encodings.** Every text read or write names its encoding.
- **Write-once raw.** Output goes to a new dated folder under the entry's
  `gcs:` (reuse `terrain.acquire._free_prefix`). `_MANIFEST.json` is the
  last object created (`terrain.manifest.write_manifest`, as `run_script`
  does). Nothing is uploaded until every check has passed.
- **Tests** never touch the network, GCS or BigQuery. Sessions, fetchers
  and stores are fakes passed in.

### Data contracts (the shared schema)

Each contract lists the stored Parquet's columns, in this order and with
these polars types, whatever the source:

- `ibama_autos.parquet`:
  - `fonte` (Utf8: `ibama` or `basedosdados`)
  - `formato` (Utf8: `sicafi` if `data_auto` is before 2019-10-08, `aie`
    from that day on, null if `data_auto` is null)
  - `id_auto` (Utf8), `data_auto` (Date), `ano` (Int64)
  - `id_municipio` (Utf8), `sigla_uf` (Utf8)
  - `latitude` (Float64), `longitude` (Float64)
  - `tipo_infracao`, `tipo_auto`, `situacao_auto`, `indicador_cancelado`,
    `gravidade`, `indicador_coordenada_valida` (Utf8)
  - `data_extracao` (Date)
- `ibama_embargos.parquet`:
  - `fonte` (Utf8)
  - `id_embargo` (Utf8), `id_auto` (Utf8), `data_embargo` (Date),
    `ano` (Int64)
  - `id_municipio` (Utf8), `sigla_uf` (Utf8)
  - `latitude` (Float64), `longitude` (Float64), `area_ha` (Float64)
  - `tipo_area`, `indicador_desembargado`, `indicador_coordenada_valida`
    (Utf8)
  - `data_extracao` (Date)

Values are stored as the source gives them: no filter by category and no
recoding of the indicators. The build (s4) filters and recodes. On the
portal path, `indicador_coordenada_valida` and `data_extracao` are null.
The 2019-10-08 change is IBAMA's switch from Sicafi (numeric numbers with
a series) to AIe (alphanumeric, no series). The record id is
`SEQ_AUTO_INFRACAO` / `id_auto` in both formats. `formato` records which
format each record is.

The contracts also hold the stored file's name and folder, the manifest's
fields (below), and the fallback rule.

### Flow of one run (both datasets)

1. **Probe the portal.** Send one HEAD request to the `portal.page` URL and
   record the HTTP status or error (no body is read).
2. **Portal path, attempted only if the mapping is complete.** The mapping
   is complete when `delimiter`, `encoding`, every `files[].url` and every
   `columns` value (except `indicador_coordenada_valida` and
   `data_extracao`, which may be null) are non-null. If it is not
   complete, skip to the BigQuery path and record "portal skipped: mapping
   incomplete". If it is complete:
   - Download each file to a temporary folder.
   - Check each file (zip opens; the header holds every mapped column).
   - Read only the mapped columns, typed to the schema. The coordinates
     file fills `latitude` and `longitude` only where the main file's are
     null, using the point with the smallest `order` for the key.
   - Delete the downloads.
   - Any exception on this path (HTTP error, timeout, refused connection,
     size mismatch, a failed check, a missing column, a value that will
     not type) ends the portal path. Record a reason line that holds no
     data value, and fall back.
3. **BigQuery path.**
   - Credentials: `google.auth.default(scopes=[bigquery.scope])`.
   - Session: `google.auth.transport.requests.AuthorizedSession`.
   - Billing project: `os.environ["GOOGLE_CLOUD_PROJECT"]`. The
     data-pipeline job's auth step sets it to the repository's
     `GCP_PROJECT_ID`, as `terrain.earthengine` already relies on.
   - The query is built from the catalog only. Identifiers must match
     `^[a-z_][a-z0-9_]*$` and the table `^[a-z0-9_-]+\.[a-z0-9_]+\.[a-z0-9_]+$`.
     Anything else raises. The query is
     `SELECT <columns> FROM `<table>` WHERE sigla_uf IN (<states>) AND ano BETWEEN <y0> AND <y1> ORDER BY <order_by>`.
   - First run the same WHERE with `SELECT MAX(data_extracao), COUNT(*)`.
     If the latest manifest in the entry's folder has `fonte` basedosdados,
     the same query text, the same maximum and the same count, return
     status `unchanged` and upload nothing.
   - Otherwise send `jobs.query`: POST `<endpoint>projects/<project>/queries`
     with `useLegacySql: false`, `location`,
     `maximumBytesBilled: "20000000000"`, a page size and a timeout.
   - If `jobComplete` is false, poll `jobs.getQueryResults` until it is
     true. Then page through `getQueryResults` with `pageToken`, using
     the `location` in the response's `jobReference` (US unless the job
     reports another).
   - Rows are typed from the response's `schema.fields` (INT64, FLOAT64,
     DATE, STRING, nulls kept).
   - The run fails (AcquireError, nothing uploaded) when:
     - `totalRows` differs from the rows received;
     - a column of the response is not in the catalog list;
     - the HTTP status is not 200;
     - the response has an `errors` field.
   - Rename nothing. The Base dos Dados names are the schema; add `fonte`
     and, for fines, `formato`.
4. **Write and upload.**
   - Write `ibama_autos.parquet` or `ibama_embargos.parquet` locally, in the
     schema above, sorted by `order_by`.
   - Check its size against 2 GB (`max_size_gb` in the campaign).
   - Upload it to the new dated folder, then the manifest.

### Manifest

`terrain.manifest.build_manifest` with `stage="acquire"`:

- `files`: the one Parquet, with its SHA-256 and bytes.
- `sources`: one entry for the source used.
  - Portal: each file's URL, `last_modified` and bytes.
  - BigQuery: `fonte: basedosdados`, `table`, `query` (the exact text
    sent), `location`, `max_data_extracao`, `rows`, `total_bytes_processed`,
    `job_id`.
- `notes`, one line each:
  - the source used;
  - the portal probe's status and why the portal path was skipped or
    failed;
  - the sorted distinct values of `tipo_infracao`, `tipo_auto`,
    `situacao_auto`, `indicador_cancelado` and `indicador_coordenada_valida`
    (fines), or of `tipo_area`, `indicador_desembargado` and
    `indicador_coordenada_valida` (embargoes), with null shown as `null`.
    These are values only, without counts, so step s4's filters can be
    checked against them.

No credential, access token or header value goes into the manifest or a
log: the workflow refuses a manifest that looks like one.

## Out of scope

- Any filter by category, cancellation, municipality polygon or cell: that
  is step s4.
- Polygons (`geometria`, the portal's WKT): not used in this campaign.
- Changing the generic acquirer, the data-pipeline workflow or any test
  already in the repository.

   with exactly the contract's columns and types, `fonte` =
   `basedosdados`, and a manifest whose `sources` hold the query and
   `max_data_extracao`.
5. With an incomplete portal mapping, the portal files are never requested
   (only the HEAD probe), and the notes say "portal skipped: mapping
   incomplete".
6. With a complete synthetic mapping and fake portal files, the portal
   path writes the same schema with `fonte` = `ibama`. The synthetic files
   hold a name column and a CPF/CNPJ column with synthetic values. A test
   checks that neither the column names nor their values appear in the
   stored Parquet, the manifest or the captured log output. A missing
   mapped column makes it fall back.
7. `formato` is `sicafi` for 2019-10-07, `aie` for 2019-10-08, and null for
   a null date.
8. A second run whose `MAX(data_extracao)` and count match the latest
   manifest returns `unchanged` and uploads nothing. A new run writes to a
   new dated folder, and the manifest is the last object created.
9. The manifest notes list the distinct values named above, without
   counts.
10. `uv run ruff check .`, `uv run ruff format --check .` and `uv run pytest`
    pass.
