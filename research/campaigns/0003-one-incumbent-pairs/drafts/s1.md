# Task: count close pairs with exactly one incumbent at 0.25%, without outcomes (explore, idea 0001)

## Goal

Decision 0009 (point 5) makes the incumbency-adjusted direct estimate the
fallback, and its Z term draws only on close pairs with exactly one
incumbent. Campaign 0002 counted those pairs at 0.50% (run 42514591508,
check 1: 1,294 pooled 2008-2020). The registered window is 0.25%, and no
run has counted them there.

This task writes a script that counts, on the exploration half at the 0.25%
window, the close pairs with exactly one incumbent, by election 2008-2020
and pooled. It uses the same definitions as campaign 0002's check 1. **It
reports counts only, reads no outcome data, and does not import or run the
registered analysis.**

Campaign `research/campaigns/0003-one-incumbent-pairs/campaign.md`, step
s1. Step s2 runs the script once through `explore-run`. Its kill rule reads
`counts.pooled.one_incumbent`.

## Idea

Idea 0001 (`research/ideas/0001-electoral-strongholds.md`). It rests on
decision 0008 (`research/decisions/0008-close-race-window.md`: the window
is 0.25%, with 2,328 close pairs on this half, 2008-2020), decision 0009
(`research/decisions/0009-pap-kill-criteria.md`, points 4 and 5), and
campaign 0002's check 1 (`research/campaigns/0002-registered-new-paths/drafts/s1.md`,
run `research/explore-runs/0001/42514591508.md`). This is an explore task
(label `explore`): it may change only `explore/` and `tests/test_explore*`.

## In scope

- `explore/0001_one_incumbent_pairs.py` (new)
- `tests/test_explore_one_incumbent_pairs.py` (new)

Nothing else. In particular `src/terrain/registered/`,
`explore/0001_window.py`, `tests/world_0001.py` and `tests/test_explore.py`
are not changed.

### Why not the registered code

Before registration, the registered analysis refuses 0.25%
(`run_exploration` in `src/terrain/registered/r0001/analysis.py`). Calling
its functions directly at 0.25% would get around that guard. So **the
script must not import `terrain.registered` in any form**. Instead it
rebuilds check 1's definitions from the explore code that the registered
core was copied from:

- **Close pairs**, as `treatment_year` in `analysis.py` builds them, using
  `terrain.strongholds` only: `main = sh.main_election(cv)`, then
  `sh.close_pairs(sh.margins(sh.within_list_pairs(sh.candidacy_votes(cv, year, main)), sh.valid_votes(turnout, main)), window)`.
- **Incumbency**: `incumbent(cands, year)` from `explore/0001_window.py`,
  loaded with importlib as that script loads `0001_effects.py`, not copied.
  It is the same function as `frozen.incumbent`. Candidates come from that
  module's `load_candidates(store, tmp, half)`: council candidacies
  2004-2024 of the exploration half, with 2004 needed for 2008's
  incumbency.
- **The sign per pair**, as `incumbent_sign` in `analysis.py` defines it:
  `+1` if only the winner (`w`) held the seat (incumbent 1.0 for `w` and 0.0
  for `l`); `-1` if only the loser (`l`) did; `0` otherwise (both, neither,
  or either side null or unmatched). The few lines of this rule are written
  in the script, since it cannot import them.

### What runs

`uv run python explore/0001_one_incumbent_pairs.py --out-dir DIR`, through
`explore-run` with `script=0001_one_incumbent_pairs`. It calls
`exploration_municipalities` and `restrict` like every explore script. The
window is a constant 0.0025 (0.25%). Elections are 2008, 2012, 2016 and
2020.

It reads the exploration half of these files only, through the build
manifests (`data/manifests/build/`), as `explore/0001_window.py`'s
`make_reader` and `load_candidates` do:

- `tse_candidates`: `candidates.parquet` (the columns of `0001_window.py`'s
  `CAND_COLUMNS`);
- `municipalities`: `municipalities.parquet` (`cd_ibge`, `cd_tse`);
- `tse_results`: `candidate_votes_<year>.parquet` and
  `turnout_<year>.parquet` for 2008, 2012, 2016 and 2020.

**Outcome data in scope (referee R2): none.** It reads no `cell_outcomes`,
`grid_cells`, `cell_exposure`, `cell_displacement`, `section_votes`,
polling-place or other file, and no outcome year. It computes nothing
beyond the counts below (referee R7).

Voter IDs (`nr_titulo_eleitoral_candidato`) are used in memory by
`incumbent` only. They never reach `results.json`, `summary.md`, logs or
exception messages (AGENTS.md, "Personal identifiers").

### What `results.json` holds

Written with `write_results`. Keys never contain dots, and elections are
keyed `e2008` .. `e2020`. Every count is a whole number.

- `counts.e<year>.plus`, `.minus`, `.zero`, `.one_incumbent` (plus +
  minus) and `.pairs` (all close pairs of that election at 0.25%), for 2008,
  2012, 2016 and 2020.
- `counts.pooled.plus`, `.minus`, `.zero`, `.one_incumbent` and `.pairs`,
  summed over 2008-2020.
- `window`: the text `"0.25%"`, not a number.
- `elections`: the list `[2008, 2012, 2016, 2020]`.

The kill rule of step s2 reads `counts.pooled.one_incumbent` (it kills the
step below 200). It must be written at exactly that path, as a whole number.

`summary.md`: the first line is "Pairs with exactly one incumbent at 0.25%,
pooled 2008-2020: N". Then one row per election and a pooled row, with plus,
minus, zero, one_incumbent and pairs. Then one line comparing the pooled
pairs with decision 0008's 2,328 (equal or not; the number is a constant in
the script, used for that line only). Then the caveats: exploration half
only; counts of treatments, not outcomes; no estimate; the registered
analysis was not run.

### Never

- Any import of `terrain.registered`, in the script.
- Any read of an outcome file, `sealed/` or `confirm/`.
- Any estimate, p-value, share, mean or other floating-point number in
  `results.json` or `summary.md`.
- Any other window.

## Out of scope

- Every other file, including the idea file and `research/lessons.md`. In
  a campaign, the tracking issue's ledger stands in for both until the
  close-out.
- Any other window, estimate, or comparison with earlier runs beyond the
  one pairs line in `summary.md`.
