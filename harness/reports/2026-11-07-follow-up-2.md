## 2. Results

### confirm-run and unblind (PR #236)

**What it does.** confirm-run runs a registered spec on the confirmation
half with each close pair's sides swapped by a coin flip, and opens a
ledger PR. unblind runs the same spec with the real treatment after your
approval, once. It refuses if:
- the ledger has no shuffled run of the same spec, byte for byte;
- that shuffled run found something (a confirmatory p below 0.05), unless
  you dispatch it with `accept_failed_shuffle`;
- the spec was unblinded before;
- its claim branch `ledger/unblind-<spec>` exists.

**Safeguards.** The shuffle's seed comes from the spec's hash, so repeated
shuffled runs give the same numbers and cannot be averaged. An analysis can
read outcomes only after it has taken its treatment through `assign`. Its
results may hold numbers and short names only.

**Tests.** On synthetic data with a true effect of 1.0, the shuffled run
gives 0.04 (p 0.62) and the real run gives 1.06 (p 0.001). A mutation that
skips the shuffle fails 4 tests. The full suite passes (763 tests), and
CI passes on the PR.

**Limits.** It has not run in Actions: a manual workflow can be started
only once it is on main. No registered analysis exists yet. The plan's
estimator still has to be written as a module under
`src/terrain/registered/`.

**Judgement calls you may want to check:**

- **The incumbency term.** As you wrote it, D^inc flips with each pair, as
  D does. The earlier proposal Z (incumbent side minus the other side) does
  not. With D / 2 and D^inc / 2 in one regression, the coefficient on D / 2
  is the effect around non-incumbent sides, and the one on D^inc / 2 is how
  much the effect differs around incumbents. The RI test stays valid. But a
  term that flips with the pair does not absorb a fixed difference between
  incumbent and non-incumbent sides, which was the balance concern. The
  draft uses your wording and adds a note (section 4). I did not
